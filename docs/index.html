Documentation

k3sm is a macOS-native Kubernetes distribution for Apple Silicon — the macOS/arm64 analog of k3s. Pods run as native Darwin processes (no Linux, no containers, no VM by default). This directory is the front door to the user-facing docs; read them roughly in the journey order below.

These pages describe user-visible behavior. The authoritative product design lives in the design document.

Read in Order#

  1. Quickstart — one node, first Pod, in a few minutes.
  2. Installation — what k3sm install does, the one-time admin step, the _k3sm posture.
  3. Concepts — how k3sm maps Kubernetes onto native Darwin processes.
  4. Cluster access — getting a kubeconfig and talking to the cluster.
  5. Supported workloads — the OCI images k3sm runs, what it refuses, and the path from a Dockerfile to a running Pod.
  6. Images — the reference: both workload conventions, k3sm build, image load/import/push, and every deliberate difference from the docker verb of the same name.
  7. Node-local registry — the loopback OCI registry: push a locally built image and pull it back through the ordinary Kubernetes image path.
  8. Storage — local-path PVs, node affinity, what is and isn’t supported.
  9. Version support — the Kubernetes version k3sm tracks and how to read the live pin.
  10. Upgrades — upgrading a node or cluster, the launchd restart model.
  11. Certificates — the two CAs, k3sm certificate rotate, and what it does not do.
  12. Backup and restore — the kine/SQLite datastore: k3sm snapshot save/restore, the automatic pre-migration copy, and the restore drill.
  13. Multi-node clusters — joining agents, the mesh, EXPERIMENTAL status.
  14. High availability — HA control plane, EXPERIMENTAL status.
  15. Linux images — the intended isolation boundary for untrusted workloads: it boots linux/arm64 images per Pod today.
  16. MLX serving — serving a model on the Mac’s GPU through an OpenAI-compatible endpoint.
  17. Limitations — the real gaps.
  18. Troubleshooting — logs, common failures, recovery.
  19. FAQ — short answers to the common questions.

Before You Build Anything Real#

k3sm is not a drop-in replacement for a Linux Kubernetes cluster. Workloads must be adapted, and several standard behaviors diverge by design. Read Limitations first — it cites the canonical conformance registers so nothing there is rosier than the truth.

MLX / Apple-GPU workloads (the MLXModel CRD and the mlx.k3sm.io/gpu extended resource) have their own page — see MLX quickstart, item 16 above. The rest of these pages describe the general workload path.
