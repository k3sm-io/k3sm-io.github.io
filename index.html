kubernetes for macOS, natively

k3sm is the macOS/Apple-Silicon analog of k3s: a single-binary Kubernetes distribution whose Pods run as native Darwin processes by default. The vm RuntimeClass runs linux/arm64 images in a per-pod micro-VM.

k3sm is the macOS and Apple-Silicon analog of k3s: the upstream Kubernetes control plane in one binary, with the substrate underneath rebuilt on macOS’s own primitives — Seatbelt, lo0, wireguard-go, launchd, APFS. Pods run as native Darwin processes. The vm RuntimeClass runs linux/arm64 images in per-pod micro-VMs.

Builds install via the script below; the Homebrew tap and notarized package land with the first stable release.

Get Started#

Apple Silicon, macOS 26 or newer:

curl -fsSL https://k3sm.io/install.sh | sh

The script resolves the newest release, verifies its checksums, and runs sudo k3sm install — it shows you exactly what it will do before asking for anything. Pin a version with K3SM_INSTALL_VERSION; install covers every channel. To build from source instead:

for r in apis runtimed darwin-net k3sm; do git clone https://github.com/k3sm-io/$r; done
go work init ./apis ./runtimed ./darwin-net ./k3sm
cd k3sm && CGO_ENABLED=1 go build -o k3sm ./cmd/k3sm
sudo ./k3sm install

The installed launchd daemon starts the control plane and registers the Mac as a node. The first manifest — and the kubernetes.io/os: darwin selector every k3sm Pod needs — is in the quickstart.

A Pod is then a native binary your Mac scheduled, sandboxed, and is supervising:

$ k3sm kubectl apply -f examples/hello-native.yaml
pod/hello-native created

$ k3sm kubectl get pods
NAME           READY   STATUS    RESTARTS   AGE
hello-native   1/1     Running   0          4s

$ pgrep -fl 'tail -f /dev/null'
48213 /usr/bin/tail -f /dev/null

There is no container, VM, or shim between the Pod and the process table: kubectl scheduled it, Seatbelt confines it, launchd keeps its supervisor alive, and ps sees an ordinary macOS process.

What People Run on It#

CI for Apple platforms

Build agents, test runners, signing and notarization steps are already native macOS binaries. Run them as Deployments, Jobs and CronJobs handled by the real upstream controllers, on the Macs you already have.

MLX model serving on Apple GPUs

An MLXModel custom resource and an mlx.k3sm.io/gpu extended resource reconcile a model into a served, OpenAI-compatible endpoint on the Mac’s own unified memory. Validated on hardware.

Linux images in per-pod micro-VMs

A Pod that names the vm RuntimeClass boots a linux/arm64 OCI image in its own Virtualization.framework guest and reaches Running . kubectl exec -it and kubectl attach give it a real terminal. linux/amd64 is a later release.

Build container images in the cluster

k3sm build -t myapp:dev . builds any Dockerfile. One that RUNs commands builds on the cluster — buildkit in a micro-VM, started for you on first use — and the image lands in the node’s store either way. No external build service, and no separate container engine to install.

A fleet of Macs as one cluster

Join more Macs with a single token over a wireguard-go mesh; each node keeps its own pod range and traffic is routed, not translated. A joined worker schedules Pods, serves NodePorts across nodes, and resolves cluster DNS in-Pod .

Why It Is Not Another Linux VM#

1signed binary

upstream control plane

One binary supervises kube-apiserver, scheduler and controller-manager, built from source for darwin/arm64, over kine → SQLite. RBAC, admission, CRDs and the scheduler are the same upstream components.

0VMs on the default path

posix_spawn under Seatbelt

Containers are posix_spawn’d at host paths under a generated default-deny Seatbelt profile with an APFS clonefile root, so your app reaches the Mac’s own frameworks with nothing in between. Linux images opt in to the vm RuntimeClass and get a micro-VM per Pod.

26+macOS, on Apple silicon

full Pod lifecycle

The node milestone runs green end to end on real hardware: Seatbelt-confined Pods, the full lifecycle, logs / exec / top. what runs covers the workloads the default path takes.

What Replaces Each k3s Component#

k3sm keeps the parts of Kubernetes that make it Kubernetes — the upstream control plane, built from source for Darwin — and rebuilds everything that assumed Linux as native macOS engineering. The full walk-through, from kubectl apply down to posix_spawn, is on architecture.

k3s (Linux) k3sm (macOS-native)

apiserver / scheduler / controller-manager
the same components, built from source upstream
etcd
kine → SQLite upstream
CoreDNS
the same, plus a getaddrinfo shim in pods upstream + native
kubelet
Virtual Kubelet + a Darwin provider — logs, exec and top are provider-built native
containerd + runc
k3sm-runtimed — Seatbelt at host paths, APFS, posix_spawn, userspace limits native
Flannel
lo0-alias pod IPs and a wireguard-go mesh native
kube-proxy
a userspace Service proxy native
systemd / OpenRC
launchd, an app-bundle-wrapped daemon native

What k3sm Does Not Do#

  • Does not run Linux images on the default path — a Linux image is refused at pull there; the vm RuntimeClass runs linux/arm64 images, and linux/amd64 is a later release.
  • Does not pass CNCF [Conformance] — the suite requires Linux containers, cgroups and CNI; the conformance profile states what is claimed instead.
  • Does not isolate tenants on one node — every Pod runs as the same unprivileged _k3sm user under its own Seatbelt profile.
  • Does not enforce CPU limits as millicores — memory is sampled and can drive an OOMKill; CPU gets QoS, not a ceiling.
  • Does not enforce NetworkPolicy as a security boundary — it applies to Service-VIP ingress only.

The full inventory — volumes, DNS, restartPolicy, which addresses Services answer on — is on limitations.
