kubernetes for macOS, natively

k3sm is the macOS/Apple-Silicon analog of k3s, a single-binary Kubernetes distribution whose Pods run as native Darwin processes by default. The vm RuntimeClass runs linux/arm64 images in a per-pod micro-VM.

Download for Mac get started

Open source under Apache-2.0; contributions are DCO signed.

A Pod is a Mac process

k3sm is the macOS and Apple-Silicon analog of k3s: the upstream Kubernetes control plane in one binary, on Macs. Where a desktop container tool puts Linux containers in a VM, k3sm runs Mac processes as Pods (compare).

Native by default, Linux when asked

Apple-platform builds and tests, Metal and CoreML jobs, and inference on the Apple GPU run on the host as Pods. A Pod that names the vm RuntimeClass boots a linux/arm64 image instead.

Several Macs, one cluster

Join as many Macs as you have, one token each. Multi-node is experimental and the Thunderbolt interconnect is alpha.

Get Started#

Two ways install the same k3sm, on Apple Silicon with macOS 26 or newer.

The app. A menu bar status item and a window onto the node; it installs k3sm, offers its updates, and shows what is running.

Download for Mac

Version 0.2.3 (289 MB) for Apple silicon and macOS 26 or newer, Developer ID signed and notarized by Apple.

The install script. One command from the terminal; install covers pinning a version and every other channel, and the quickstart has building from source.

curl -fsSL https://k3sm.io/install.sh | sh

Either way, the installed launchd daemon starts the control plane and registers the Mac as a node. Two commands tell you whether it came up:

k3sm status    # one screen: daemons, apiserver, node, workloads, data root
k3sm doctor    # preflight checks for this Mac, each with its fix

sudo k3sm stop shuts k3sm down completely and keeps it down across reboots, and sudo k3sm start brings it back (stopping and starting). The quickstart has the first manifest, including the kubernetes.io/os: darwin selector every k3sm Pod needs.

The first Pod, shown at the top of this page, is a native binary your Mac sandboxes and supervises.

No container or VM sits between the Pod and the process table. kubectl scheduled it, Seatbelt confines it, launchd keeps its supervisor alive, and ps sees an ordinary macOS process.

What People Run on It#

CI for Apple platforms

Build agents and test runners are already native macOS binaries. Run them as Deployments, Jobs and CronJobs under the upstream controllers, on Macs you already have.

MLX model serving on Apple GPUs

An MLXModel custom resource and an mlx.k3sm.io/gpu extended resource reconcile a model into a served /v1/chat/completions endpoint in the Mac’s unified memory.

Linux images in per-pod micro-VMs

A Pod that names the vm RuntimeClass boots a linux/arm64 OCI image in its own Virtualization.framework guest and reaches Running, on a single node. kubectl exec -it and kubectl attach give it a terminal. linux/amd64 is a later release.

Build container images in the cluster

k3sm build -t myapp:dev . builds any Dockerfile into the cluster registry. A copy-only one becomes a darwin/arm64 image; one that RUNs commands becomes a linux/arm64 image, built by BuildKit in a micro-VM that starts on first use. No external build service or container engine is needed.

A fleet of Macs as one cluster

Join more Macs with a single token over a wireguard-go mesh. Each node keeps its own pod range, routed without NAT. A worker schedules Pods, serves NodePorts across nodes, and resolves cluster DNS in-Pod. Two Macs can also share the control plane on embedded etcd (high availability); two servers tolerate no server failure. Both are experimental, and multi-node graduates in a later release on the roadmap.

What Replaces Each k3s Component#

k3sm keeps the upstream control plane and rebuilds everything that assumed Linux on macOS. The walk-through from kubectl apply down to posix_spawn is on architecture.

k3s (Linux) k3sm (macOS-native)

apiserver / scheduler / controller-manager
the same components, built from source upstream
etcd
kine → SQLite, or embedded etcd for an experimental two-server control plane upstream
CoreDNS
a per-node in-process resolver on the cluster DNS address, plus a getaddrinfo shim in pods native
kubelet
Virtual Kubelet + a Darwin provider (logs, exec and port-forward are provider-built) native
containerd + runc
k3sm-runtimed (Seatbelt at host paths, APFS, posix_spawn, userspace limits) native
Flannel
lo0-alias pod IPs and a wireguard-go mesh native
kube-proxy
a userspace Service proxy native
systemd / OpenRC
launchd, an app-bundle-wrapped daemon native
helm-controller, auto-deploying manifests
HelmChart and HelmChartConfig in helm.k3sm.io/v1, with the same fields as k3s, and manifests in a root-owned directory applied automatically native

What k3sm Does Not Do#

  • Does not run Linux images on the default path, where they are refused at pull. The vm RuntimeClass runs linux/arm64 images; linux/amd64 is a later release.
  • Does not pass CNCF [Conformance], which requires Linux containers, cgroups and CNI. The conformance profile states what is claimed.
  • Does not isolate tenants on one node, because every Pod runs as the same unprivileged _k3sm user under its own Seatbelt profile.
  • Does not enforce CPU limits. Memory is sampled and can drive an OOMKill or an eviction; CPU gets QoS and no ceiling.
  • Does not enforce NetworkPolicy as a security boundary. Each node applies it to Service-VIP ingress for its own Pods only, and direct Pod-IP traffic bypasses it.

limitations has the complete list, including volumes, DNS, restartPolicy, and which addresses Services answer on.
