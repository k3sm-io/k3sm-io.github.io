Compare

A side-by-side of k3sm against Kubernetes in a Linux VM on a Mac, and against a real Linux Kubernetes cluster.

k3sm and the VM-based tools answer different questions. This page compares them point by point.

Three things are being compared:

  • Kubernetes in a Linux VM on your Mac: Docker Desktop, Rancher Desktop, minikube, kind, Colima, OrbStack, k3s inside Lima. Architecturally these are one thing: Linux Kubernetes in a guest, with ports and directories forwarded back to the host.
  • A real Linux Kubernetes cluster: anything from a managed cloud offering to k3s on hardware.
  • k3sm: Kubernetes whose nodes are Macs and whose Pods are Darwin processes.

Where k3sm Loses#

  1. An amd64-only Linux image does not run at all. It is refused at pull on both paths — the default path wants darwin/arm64, the vm path wants linux/arm64. An unmodified linux/arm64 image does run: adding runtimeClassName: vm boots it in a per-Pod micro-VM on a single node. On the default path a Pod is a Mac binary, so a workload that has to run there is rebuilt, not relabelled — though registry, tags, digests and pull secrets all behave as expected (what runs). A Linux VM tool runs any Linux image, amd64 or arm64, today, mature and free.
  2. It is not CNCF-conformant, and there is no path to becoming so. The suite requires Linux containers, cgroups, CNI, and network namespaces; k3sm has none of them by construction. k3sm cannot provide a Certified Kubernetes badge.
  3. The release line is younger. Today the install is the script and builds are pre-releases; the Homebrew tap, the notarized package, and a supported-versions policy come with the first stable release planned. There is no support contract on offer.
  4. The isolation model is weaker. Same-node native Pods share a uid and a port space. Seatbelt bounds what each Pod can reach, but it is neither a namespace nor a tenancy boundary. A Pod can name the vm RuntimeClass for a per-Pod micro-VM boundary instead — linux/arm64 only.
  5. The resource model is weaker. CPU limits are accounting and QoS, never a millicore ceiling. Memory limits are sampled proc_pid_rusage followed by SIGKILL — best-effort, not a cgroup guarantee. There is no node-pressure eviction guarantee; memory pressure ends in a per-Pod kill.
  6. NetworkPolicy is not a security boundary. It applies to Service-VIP ingress only — no egress, no ipBlock.
  7. No benchmarks. k3sm publishes no performance numbers because none have been measured.

And Where It Wins#

  1. Your workload can be a Mac. Xcode, codesign, notarization, Metal, CoreML, the keychain, full-speed local disk at real host paths: all reached directly, because there is no guest between the Pod and the OS. MLX model serving runs on the Apple GPU .
  2. A room full of Macs becomes a cluster. Real nodes, one token to join, the real scheduler placing work on them, Pod traffic routed over a wireguard mesh .
  3. The API is the upstream one. Your manifests, RBAC, CRDs, and controllers are the same ones you use everywhere, because the control-plane binaries are the same ones.
  4. No always-on guest. Native Pods are processes. Only a vm Pod adds a micro-VM, one per Pod, created when the Pod starts.

How to Choose#

  • For a full Linux development environment on a Mac, or for amd64: a Linux VM tool. For running a single arm64 Linux image inside a k3sm Pod, the vm RuntimeClass does that directly.
  • For a production Kubernetes cluster: Linux Kubernetes — the platform the ecosystem builds for, certifies, and supports.
  • For orchestrating work that must run on macOS (builds, signing, Apple-platform tests, on-device inference) through the Kubernetes API: that is the case k3sm was built for, and nothing else is currently trying to serve it.
