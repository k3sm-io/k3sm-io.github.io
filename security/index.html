Security

How to report a vulnerability in k3sm: the private GitHub advisory flow first, then email, then the maintainer. Plus the trust boundaries.

k3sm runs privileged components (a root networking helper and a process sandbox), so a public bug report is a disclosed zero-day before there is a fix. Please report privately.

Reporting a Vulnerability#

Do not open a public GitHub issue for a security problem. Use these channels, in this order of preference:

  1. GitHub private security advisories. Open the affected repository’s Security tab and choose Report a vulnerability. This is the preferred channel: it is private, it supports coordinated and embargoed collaboration, and a CVE can be issued from it. Direct links: k3sm, runtimed, darwin-net, apis. If you are unsure which repository is affected, use k3sm.
  2. Email — kitsumiko@k3sm.io. Use this if the advisory flow is unavailable to you, or if you would rather not open a GitHub account to make a report.
  3. Direct contact — message the maintainer @kitsumiko on GitHub.

Please include the affected component and a reproduction if you have one.

What Counts as High Severity#

These classes matter most:

  • Local privilege escalation: anything that gets from the unprivileged _k3sm user, or from inside a Pod, to root. The k3sm-netd helper is the only root component and it accepts a closed, typed RPC over a uid-authenticated socket; a way to make it act outside that contract is a serious finding.
  • Sandbox escape: anything that lets a Pod’s process reach outside its generated Seatbelt profile: reading /Users, writing outside its own data volume, or reaching another Pod’s files.
  • Guest kernel or initramfs substitution: the vm RuntimeClass’s guest kernel and initramfs are digest-pinned artifacts, and the pin is the whole trust chain — a VM-booted kernel gets no OS code-signing check. A way to have the guest boot an unpinned kernel or initramfs is a serious finding.

Also serious: a way to join a cluster without the join credentials, a way to impersonate a node, a flaw in certificate issuance or trust, and anything that undermines the code-signing and notarization chain.

What Is a Documented Limitation, Not a Vulnerability#

These are stated in advance in limitations, and are design trade-offs rather than bugs. A report is still welcome as a discussion, just not as an embargoed advisory.

  • Same-node Pods share one trust domain. Every Pod on a node runs as the same _k3sm user. There is no per-Pod uid isolation and no network namespace. The vm RuntimeClass now boots a Pod into its own micro-VM, with the supervisor process itself confined on the host, but the path is linux/arm64 only and not yet a general alternative for untrusted work on this node.
  • NetworkPolicy is a policy hint. It is enforced only on Service-VIP-mediated ingress; direct Pod-IP traffic bypasses it, and egress rules and ipBlock are not enforced. It is not a security boundary.
  • Seatbelt network permission is all-or-nothing. macOS accepts no per-address filters in a sandbox profile, so a Pod that may use the network may use all of it. The per-Pod egress opt-in is an admission-level contract, not a packet filter.
  • Pods share one port space with the node. With no network namespaces, a Pod and a LoadBalancer listener can collide on a port.

A new case in one of these classes, one the pages do not describe, is worth reporting. So is documentation that describes a boundary as stronger than it is.

Disclosure#

k3sm follows coordinated disclosure: a report is acknowledged, a fix is worked under embargo, and — unless you would rather not be — you are credited when the fix is released.

Supported Versions#

Please report against the latest main. A supported-versions policy is published with the first stable release planned.

The canonical policy is SECURITY in the repository; this page mirrors it.
