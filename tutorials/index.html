Tutorials

A ladder from your first native Pod to the things k3sm will not do, with each step marked by how far it has been validated.

Twelve short walk-throughs, in order. The first six are the working core of k3sm today: install a node, run a Pod, front it with a Service, give it storage, probe it, and give it stable identity. The next five reach into paths that are partly built, and each one says exactly where it stops. The last one produces a failure on purpose — a Linux-only binary on the native path — and shows the reason and the workaround.

Every command on these pages runs today unless it is marked otherwise. A capability that is not finished carries a badge naming the milestone it waits on, and is written in the future tense.

Before You Start#

  • Apple Silicon, macOS 26 or newer. k3sm runs Pods as native arm64 Darwin processes; there is no Intel path and no VM in the default path.
  • No k3sm release is published yet. Until the first tagged release the install script reports that cleanly and installs nothing. The install steps below are the shape of the first run, and the rest of each tutorial assumes an installed node.
  • Read limitations early. It is the inventory of what diverges and why.

Two Fields Every Pod Needs#

They appear in every manifest on every page, and a Pod without them does not run:

  • nodeSelector: kubernetes.io/os: darwin. A validating admission policy rejects any Pod that does not declare it, so kubectl apply fails and nothing is created.
  • a toleration for the k3sm.io/provider:NoSchedule taint. Every k3sm node carries it. Without a matching toleration the Pod is admitted and then sits Pending forever. Only DaemonSet-owned Pods get it injected, so a Deployment, StatefulSet, or Job template has to carry it itself.

Keep the toleration keyed on k3sm.io/provider rather than a blanket operator: Exists. A blanket toleration also tolerates node.kubernetes.io/not-ready, which keeps a Pod bound to a node that has stopped working.
